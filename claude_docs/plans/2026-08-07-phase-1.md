# Phase 1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** All of Phase 1: `core`, `pg`, `proxy`, `cli` with its daemon, hibernation, `studio`, `mcp`, plus the M0 spike code and the eject invariants.

**Architecture:** An npm workspace of six packages. One daemon owns SQLite state and lifecycle and serves a single HTTP control API on two listeners. The CLI, MCP and Studio are three clients of that API and none of them touches Docker or Postgres directly. A wire proxy fronts 5432, routes on the database name, wakes a stopped instance, and is also the activity sensor hibernation reads.

**Tech Stack:** TypeScript. Node 24 (Bun is the intended shipping runtime per ADR 0006 but is not installed here). `node:test` and `node:assert` for tests, which both runtimes support. `pg` as the Postgres client. `better-sqlite3` for state. Docker via the CLI. React and Vite for Studio.

## Global Constraints

- **No em-dashes anywhere.** Docs, code, comments, commit messages, user-facing output.
- **Source imports only from `node:*` and declared dependencies.** No `Bun.*` APIs. From ADR 0006.
- **Postgres is unmodified.** Stock upstream image, no patches, no required extensions.
- **The data directory is a plain `PGDATA` on the host**, bind mounted. Nothing of ours inside it. From ADR 0003.
- **The daemon API is the only control surface.** CLI, MCP and Studio never import `pg`, never shell out to `docker`, never read `state.db`.
- **`core` never imports Docker, Postgres, or HTTP.** The `ComputeRuntime` interface is the seam. From ADR 0002.
- **The proxy asks, the engine acts.** The proxy calls `wake(resourceId)` and waits. It never starts a container itself.
- **Cold start budget: under 1 second target, 3 seconds hard ceiling.**
- **Routing: the database name is the project.** `blog` reaches project `blog`; `blog.analytics` reaches database `analytics` inside it. Split on the first dot.
- **Tests are written but not executed in this run.** Every task must still leave the workspace typechecking with `npm run typecheck`. Do not claim tests pass.

## Deviations from the written specs, and why

1. **`node:test` instead of `bun:test`.** Bun is not installed on this machine. `node:test` runs on both runtimes, so this also satisfies ADR 0006's Node-compatible API rule. The M0 spike plan at `2026-08-07-m0-cold-start-spike.md` specifies `bun:test`; use `node:test` instead and keep everything else in that plan as written.
2. **npm workspaces instead of Bun workspaces**, for the same reason.
3. **Tests are not run.** The user asked for code without test execution. Typechecking is still mandatory.

  | 'creating' | 'running' | 'starting'

  id: ProjectId

export interface Resource {
  id: ResourceId

}

  image: string

}

  name: string
  image: string

  ports: Array<{ host: number; container: number }>
  binds: Array<{ host: string; container: string }>

}

  exists: boolean

}

export interface ComputeRuntime {
  available(): Promise<boolean>

export function parseRoutingKey(database: string): { project: string; database: string | null }
export function parseTarget(target: string): { project: string; resource: string | null }

}

  sleepAfterSeconds: number | null

  getProject(id: ProjectId): Project | null
  getProjectByName(name: string): Project | null
  listProjects(): Project[]
  deleteProject(id: ProjectId): void
  createResource(input: { projectId: ProjectId; kind: ResourceKind; name: string; config: PostgresConfig }): Resource
  getResource(id: ResourceId): Resource | null
  getResourceByName(projectId: ProjectId, name: string): Resource | null

  setResourceState(id: ResourceId, state: ResourceState): void
  touchResource(id: ResourceId, at: Date): void
  updateResourceConfig(id: ResourceId, config: PostgresConfig): void
  deleteResource(id: ResourceId): void

  close(): void

**Requirements:**

- `validateName`: `^[a-z][a-z0-9-]{1,62}$`, and reject `postgres`, `template0`, `template1`, `hobby`. Throw `HobbyError('invalid_name', ...)` with a hint naming the rule.
- `parseRoutingKey('blog')` returns `{ project: 'blog', database: null }`. `parseRoutingKey('blog.analytics')` returns `{ project: 'blog', database: 'analytics' }`. Split on the FIRST dot only, so `blog.a.b` gives database `a.b`.
- `parseTarget` follows the same shape for CLI targets but splits on `/`.
- `HobbyError.httpStatus`: `not_found` codes 404, `name_taken` and `conflict` 409, `usage` and `invalid_name` 400, `unauthorized` 401, `runtime_unavailable` 503, `wake_timeout` 504, everything else 500.
- `resolvePaths`: home is `$HOBBY_HOME` or `~/.hobby`. `resourceDataDir` is `<projectsDir>/<project>/<resource>/pgdata`.
- `resolveConfig` precedence, highest first: flags, `HOBBY_*` environment variables, `hobby.json` found by walking up from `cwd`, then defaults. Defaults: image `postgres:18-alpine`, proxyPort 5432, studioPort 8443, apiPort 7432, sleepAfterSeconds 300, wakeTimeoutMs 30000, readinessPollMs 25.
- `openStore` uses `better-sqlite3`, creates tables if absent, stores dates as ISO strings and `config` as JSON. `allocatePort` returns the lowest free port in range not already recorded in any resource config.
- `createFakeRuntime` is an in-memory `ComputeRuntime` used by every later task's tests, so no test needs Docker.

**Tests to write (not run):** name validation accepts and rejects the documented cases; routing key splits on the first dot only; `HobbyError` maps each code to the documented status; store round-trips a project and a resource and enforces unique names; `allocatePort` skips a taken port.

**Done means:** `npm run typecheck` passes at the repo root.

**Commit:** `feat(core): resource model, state store, errors, config`

### Task 2: Docker `ComputeRuntime`

**Files:**
- Create: `packages/core/src/docker.ts`

- Modify: `packages/core/src/index.ts` to export `createDockerRuntime`

**Interfaces:**
- Consumes: `ComputeRuntime`, `ContainerSpec`, `ContainerStatus` from Task 1
- Produces: `export function createDockerRuntime(exec?: ExecFn): ComputeRuntime` where `export type ExecFn = (cmd: string, args: string[]) => Promise<{ stdout: string; stderr: string }>`

**Requirements:**

- Shell out to the `docker` CLI through `node:child_process.execFile`, wrapped by the injectable `ExecFn` so tests can assert the argv without Docker present. That injection is the entire testability strategy here.
- `ensureCreated` is idempotent: inspect first, create only if absent, and return the container name as the id.
- `create` argv must include `--name`, one `-e KEY=VALUE` per env entry, one `-p host:container` per port, one `-v host:container` per bind, and `--network` when a network is given.
- `inspect` returns `{ exists: false, running: false, exitCode: null }` when Docker reports no such container, rather than throwing.
- `stop` uses `docker stop -t <timeoutSec>`, which is a clean shutdown. Never `docker kill`. A `SIGKILL`ed Postgres does recovery on the next start and that recovery lands inside a user's first query.
- `available()` returns whether `docker version` succeeds.
- Any unexpected failure becomes `HobbyError('runtime_unavailable', ...)` with the stderr as the hint.

**Tests to write (not run):** `ensureCreated` on an absent container issues `docker create` with the exact expected argv; on a present container it issues no create; `inspect` maps a "No such object" failure to `exists: false`; `stop` passes the timeout.

**Done means:** typecheck passes.

```ts
export interface PgDeps { store: Store; runtime: ComputeRuntime; paths: Paths; config: HobbyConfig }

export function createPostgres(deps: PgDeps, opts: { project: Project; name: string }): Promise<Resource>
export function startPostgres(deps: PgDeps, resource: Resource): Promise<void>
export function stopPostgres(deps: PgDeps, resource: Resource): Promise<void>
export function destroyPostgres(deps: PgDeps, resource: Resource): Promise<void>
export function waitReady(opts: { config: PostgresConfig; pollMs: number; timeoutMs: number; probe?: () => Promise<boolean>; sleepFor?: (ms: number) => Promise<void>; now?: () => number }): Promise<{ ready: boolean; attempts: number; waitedMs: number }>
export function pgProbe(config: PostgresConfig): () => Promise<boolean>
export function connectionString(project: Project, resource: Resource, opts: { host: string; port: number; viaProxy: boolean }): string
```

**Requirements:**

- `createPostgres` allocates a port, generates a 32 character random password with `node:crypto.randomBytes`, creates the data directory with `mkdir -p` and mode `0700`, creates the container with the data directory bind mounted at `/var/lib/postgresql/data`, starts it once so `initdb` runs, waits for readiness, then **stops it cleanly**. A newly created resource ends in state `sleeping`, which is the correct resting state for a system whose wedge is sleep.
- The database inside is named after the project, not `postgres`. Create it on first boot by passing `POSTGRES_DB`.
- `startPostgres` sets state `starting`, starts, waits for readiness, sets `running`, touches `lastActiveAt`. On timeout it sets `failed` and throws `HobbyError('wake_timeout', ...)`.
- `stopPostgres` sets `stopping`, stops cleanly with a 30 second timeout, sets `sleeping`.
- `destroyPostgres` stops, removes the container, removes the data directory recursively, deletes the row.
- `waitReady` takes injectable `probe`, `sleepFor` and `now` so the poll loop is testable with a fake clock and no Postgres.
- `connectionString` with `viaProxy: true` renders `postgres://<superuser>:<password>@<host>:<proxyPort>/<project>`; with `viaProxy: false` it renders the direct host port. The proxy form is what users are shown once Task 6 lands.

**Tests to write (not run):** `waitReady` returns on the first successful probe, counts attempts, respects the timeout, and waits longer with a coarser interval; `connectionString` renders both forms; `createPostgres` against the fake runtime leaves the resource `sleeping` and the config populated.

**Done means:** typecheck passes.

### Task 4: The daemon and the control API

**Files:**
- Create: `packages/cli/{package.json,tsconfig.json}`
- Create: `packages/cli/src/daemon/{server,routes,reconcile,context}.ts`
- Test: `packages/cli/test/routes.test.ts`

**Interfaces:**
- Consumes: Tasks 1 through 3
- Produces:

```ts
export interface DaemonContext { store: Store; runtime: ComputeRuntime; paths: Paths; config: HobbyConfig; activity: ActivityTracker }
export function createApp(ctx: DaemonContext): (req: IncomingMessage, res: ServerResponse) => void
export function startDaemon(ctx: DaemonContext, opts: { socketPath: string; apiPort: number | null }): Promise<{ close(): Promise<void> }>

```

**Requirements:**

- Plain `node:http`, no framework. Two listeners over one handler: a unix socket at `paths.socketPath` created with mode `0600`, and optionally a loopback TCP listener on `apiPort` bound to `127.0.0.1` only. Never bind the API to a public interface.
- Delete a stale socket file on start if no daemon answers it.
- Routes, exactly these:

```
GET    /v1/health
GET    /v1/preflight
GET    /v1/projects
POST   /v1/projects                    { name }
GET    /v1/projects/:name
DELETE /v1/projects/:name
POST   /v1/projects/:name/resources    { kind, name }
GET    /v1/resources/:id
DELETE /v1/resources/:id
POST   /v1/resources/:id/start
POST   /v1/resources/:id/stop
GET    /v1/resources/:id/connection
GET    /v1/resources/:id/logs
POST   /v1/projects/:name/eject
```

- Every error response is `{ "error": { "code", "message", "hint"? } }` with the status from `HobbyError.httpStatus`. An unexpected throw becomes `internal` and is logged with a stack, never leaked to the client.
- `GET /v1/preflight` reports: runtime available, the filesystem under `paths.home`, whether it supports reflinks, free space, and whether the proxy and studio ports are already bound. It never mutates anything, so the CLI and Studio can both call it.
- `reconcile` runs on every daemon start: for each resource, ask the runtime what is actually true and correct the recorded state. Observed reality always wins over the recorded state. A resource whose container has vanished becomes `failed`, not silently `sleeping`.
- Clean shutdown on `SIGTERM` and `SIGINT`: stop accepting, finish in-flight requests, then stop every `running` resource cleanly. An unclean stop here becomes recovery time inside a user's next first query.

**Tests to write (not run):** each route returns the documented status and shape against a fake runtime; an unknown project returns 404 with code `project_not_found`; creating a duplicate name returns 409 `name_taken`; `reconcile` corrects a resource recorded `running` whose container is absent.

**Done means:** typecheck passes.

### Task 6: The wake proxy

**Files:**
- Create: `packages/proxy/{package.json,tsconfig.json}`
- Create: `packages/proxy/src/{index,startup,proxy,activity}.ts`
- Test: `packages/proxy/test/{startup,proxy}.test.ts`

**Interfaces:**
- Consumes: `parseRoutingKey`, `HobbyError` from Task 1
- Produces:

```ts
export const PROTOCOL_3_0 = 196608
export const SSL_REQUEST_CODE = 80877103
export const CANCEL_REQUEST_CODE = 80877102
export type StartupMessage =
  | { type: 'ssl_request' }
  | { type: 'cancel_request'; processId: number; secretKey: number }
  | { type: 'startup'; version: number; params: Record<string, string> }
export function parseStartup(buf: Buffer): { message: StartupMessage; consumed: number } | null
export function buildStartupPacket(params: Record<string, string>): Buffer
export function errorResponse(severity: string, code: string, message: string): Buffer

export class ActivityTracker {
  open(resourceId: string): void
  close(resourceId: string): void
  count(resourceId: string): number
  idleSeconds(resourceId: string, now?: number): number | null
  resources(): string[]
}

export interface ProxyDeps {
  resolve(routingKey: string): Promise<{ resourceId: string; host: string; port: number; state: string } | null>
  wake(resourceId: string): Promise<void>
  activity: ActivityTracker
}
export function startPgProxy(opts: { port: number; host?: string; deps: ProxyDeps; wakeTimeoutMs: number }): Promise<{ close(): Promise<void>; port: number }>
```

**Requirements:**

- Parse the startup packet exactly as in the M0 plan: length prefix, protocol version, null-terminated key/value pairs, terminated by a zero byte. Return `null` when more bytes are needed, throw on an implausible length above 10000 or an unterminated key or value.
- **SSLRequest is answered with `N`** in this milestone, and the client retries in plaintext. Terminating TLS is required eventually because the startup packet is otherwise unreadable, and that is recorded as the next step in `docs/proxy/`, not built here.
- **CancelRequest routes to the same upstream and is never treated as a wake.** A cancel arriving for a sleeping instance is a no-op, because there is nothing to cancel.
- Resolve the target with `parseRoutingKey(params.database)`, look it up through `deps.resolve`, and if it is not running call `deps.wake(resourceId)` and wait. **The proxy never starts a container itself.**
- On any failure send a real Postgres `ErrorResponse` with a `FATAL` severity and a plausible SQLSTATE (`57P03` for not-available, `3D000` for an unknown database) and end the socket. **Never drop the socket silently**, because an unreadable connection error is the failure that makes people uninstall.
- After the upstream connects, replay the buffered startup packet verbatim and splice both directions. **Auth passes through**, so SCRAM negotiates between client and Postgres and the proxy never sees a password.
- Call `activity.open` when the upstream is spliced and `activity.close` exactly once on the first of client close, upstream close or error. Double counting here is what makes hibernation never fire.

**Tests to write (not run):** the parser cases from the M0 plan; an unknown database yields an `ErrorResponse` with `3D000`; a sleeping target calls `wake` exactly once; `ActivityTracker` counts opens and closes and reports idle seconds only when the count is zero; a close is idempotent.

**Done means:** typecheck passes.

**Commit:** `feat(proxy): postgres wake router and activity tracker`

### Task 7: Hibernation

**Files:**
- Create: `packages/cli/src/daemon/hibernator.ts`
- Modify: `packages/cli/src/daemon/context.ts` to own the `ActivityTracker` and wire the proxy's `resolve` and `wake`
- Test: `packages/cli/test/hibernator.test.ts`

**Interfaces:**
- Consumes: `ActivityTracker` from Task 6, `stopPostgres` from Task 3, `Store` from Task 1
- Produces: `export function startHibernator(ctx: DaemonContext, opts: { intervalMs: number; now?: () => number; sleepFor?: (ms: number) => Promise<void> }): { stop(): void }` and `export function shouldSleep(input: { state: ResourceState; connections: number; idleSeconds: number | null; sleepAfterSeconds: number | null; hasActiveQuery: boolean }): boolean`

**Requirements:**

- `shouldSleep` is a pure function and carries all the policy, so the decision is testable without timers, Postgres or Docker. It returns true only when the state is `running`, connections are zero, `idleSeconds` is at or above the threshold, the threshold is not `null`, and no active query is running.
- The hibernator ticks on an interval and asks `shouldSleep` per running resource. **Activity comes from the proxy's `ActivityTracker`, not from polling `pg_stat_activity`**, which is the whole point: the proxy is on the path, so the count is exact and free.
- `pg_stat_activity` is consulted exactly once, immediately before stopping, as a guard against someone who connected directly to the published port and to refuse sleeping mid-transaction. That is what `hasActiveQuery` carries.
- A resource pinned with `sleepAfterSeconds: null` never sleeps.
- Wire the daemon's proxy dependencies here: `resolve` looks the project up by routing key and returns its running host and port, and `wake` calls `startPostgres` and is **idempotent under concurrent callers**, so ten simultaneous connections to a sleeping database produce one start, not ten. Use a per-resource in-flight promise map.

**Tests to write (not run):** `shouldSleep` truth table across every input combination that changes the answer; a pinned resource never sleeps; two concurrent `wake` calls for the same resource produce one `startPostgres` call.

**Done means:** typecheck passes.

**Commit:** `feat(cli): idle hibernation driven by proxy activity`

### Task 10: Studio, the server side and auth

**Files:**
- Create: `packages/studio/{package.json,tsconfig.json,vite.config.ts}`

**Interfaces:**
- Consumes: Task 4's app
- Produces:

```ts
export function hashPassword(plain: string): Promise<string>
export function verifyPassword(plain: string, stored: string): Promise<boolean>
export class SessionStore { issue(): string; verify(token: string): boolean; revoke(token: string): void }
export class LoginThrottle { check(key: string, now?: number): void; fail(key: string, now?: number): void; succeed(key: string): void }
export function mountStudioRoutes(app: Router, ctx: DaemonContext): void

```

**Requirements, and this is security code per ADR 0008:**

- **Argon2id** via the `argon2` package for the operator credential. Never a fast hash.
- **One operator credential. No accounts, no roles, no teams.** It is created only by `hobby studio passwd` running on the box, which makes existing shell access the root of trust.
- **No self-service signup. No email-based password reset. Ever.** Losing the credential means SSH in and set a new one.
- Session cookies are `HttpOnly`, `Secure`, `SameSite=Strict`, with a random 32 byte token from `node:crypto.randomBytes` and a server-side store. Compare tokens with `crypto.timingSafeEqual`.
- `LoginThrottle` applies exponential backoff per source address and throws `HobbyError('unauthorized', ...)` without revealing whether the credential exists.
- **The API listener stays bound to `127.0.0.1`.** Caddy is the only thing that reaches it.
- `createCaddyManager` runs Caddy as a container Hobbyist manages and configures it **entirely over its admin API**, with no config files on disk. The admin port binds to loopback.
- **Print a warning on first exposure**: this auth path has not been reviewed or exercised against a live host, and the operator should read it before pointing it at the internet. Include it in the report as a required review item.

**Tests to write (not run):** a wrong password fails and a right one succeeds; the throttle backs off after repeated failures and resets on success; session tokens verify and revoke; the Caddy manager posts the expected admin API payload for a new route.
