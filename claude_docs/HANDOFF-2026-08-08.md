# Handoff, 2026-08-08

Studio is merged to `main`. This is the night after: the two follow-ups the
last review left open, the half of eject that was missing, and one bug in
`hobby new`.

## What shipped

Branch `phase-1-followups`, merged to `main`. 274 tests pass, up from 265.

**`hobby eject <project> --release`.** The promise CLAUDE.md leads with was
half-built: eject rendered a compose file and then told you, in its own
output, that hobby was still managing the project and that handing it over was
not automated. It now does the handover. Containers stopped and removed, the
project's network removed, the rows deleted, and the data directories left
exactly where they are. Default behaviour is unchanged: a bare `hobby eject`
is still a pure read.

**`hobby new` rolls back a failed create.** Three calls, and if the second
failed the project survived its own failed creation, so the obvious retry got
409 name_taken and the way out was `hobby rm` on a project you never created.

**`ActivityTracker` tracks connections by identity.** `reset()` used to
discard a live count, so a connection that outlived a stop could zero the
count of one that followed it, and hibernation would sleep a database with a
client attached. `open()` now returns a handle and `close()` takes it.

**A leaked docker network per deleted project.** Nothing in the codebase had
ever called `removeNetwork`. `DELETE /v1/projects/:name` does now.

**`pgProbe`'s `client.end()` is bounded,** matching its sibling in
activity-guard.ts, and the probe has tests for the first time.

## Eject was verified end to end, against real Docker

Not asserted, run. In an isolated `HOBBY_HOME` on its own ports, so your
daemon and your five projects were never touched:

1. `hobby new ejecttest` created it.
2. `hobby eject ejecttest --release > docker-compose.yml` handed it over.
   Container gone, network gone, `hobby ls` empty, `pgdata/18` still on disk.
3. `docker compose up -d` against that file started the same data directory.
4. `psql` from outside the container, using the credentials in the file,
   connected and queried it.

Then everything was torn down, including the root-owned pgdata (which needs a
container to remove, the same reason destroyPostgres uses one).

## Three things for you to decide

**1. `--release` has no confirmation prompt.** It is its own gate. My
reasoning: nothing is deleted, the data survives, and the compose file that
restarts it is on stdout in the same breath, so a prompt would have to be
written to stdout, straight into the middle of
`hobby eject blog --release > docker-compose.yml`. If you would rather it
behaved like `rm`, the fix is a `--yes` flag and a prompt on stderr.

**2. Two daemons on one box allocate the same host ports.** Found while
testing: my isolated daemon has its own state.db, so it allocated 15432, the
same port your `blog/primary` uses. No collision happened because blog was
asleep, but it could have. Not a bug in the supported configuration (one box,
one daemon) and I have not changed anything. Worth an ADR line if you ever
want a second daemon to be safe, and worth knowing before you test this way
yourself.

**3. I was wrong about a bug for about twenty minutes.** I wrote a test
asserting `pgProbe` hangs against a port that accepts and then goes silent,
watched it hang, and built a fix for it. The hang was my test's teardown:
`net.Server` has no `closeAllConnections`, and `server.close()` waits on
sockets it accepted. `connectionTimeoutMillis` already covers the whole
handshake. I removed the unneeded fix and kept the honest version, and the
commit message says so. Flagging it because the wrong version was committed to
nothing, but the reasoning error is the kind worth seeing.

## Still open, in the order I would take them

1. **No install path, and it is blocked on you.** ADR 0006 makes Bun the
   runtime and `bun build --compile` the install story, precisely so a bare
   VPS gets a download rather than a runtime prerequisite. Bun is not
   installed on this machine, so the ADR's own path has never been executed
   once: M0 ran on Node, and the results file says so in its name. Installing
   a runtime on your machine is not something to do while you are asleep, so
   this stops here. Two paths when you pick it up: install Bun and find out
   whether `bun build --compile` survives the native `argon2` dependency
   (that is the usual failure point, and it is the thing to test first), or
   decide the shipped artefact is an npm package instead, which contradicts
   the ADR and needs one written to replace it. Today `@hobby.sh/cli` is
   `private: true` with `"*"` workspace dependencies, so `npm i -g` cannot
   work either way without that decision.
2. **ADR 0010: minimum specs and admission control.** Measured numbers exist
   (72 MiB awake, 0 sleeping, 46MB disk). The decision does not.
3. **`arlo` is in the `failed` state** and has been all night. It is a
   deliberate test case from an earlier session, so I left it, but it is now
   the only thing in `hobby ls` that looks broken.
4. **Studio's auth path still needs a human read** before it faces a network.
   ADR 0008 makes it a security boundary; nobody but me has looked at it.
5. **No rename verb.**
6. **About twenty classes in theme.css are referenced by nothing,** mostly the
   pre-workbench `side-list` and the result header the SQL rebuild replaced.
   Left alone: the class audit checks used-implies-defined, and the reverse
   check needs an allowlist for classes built dynamically (State.tsx's
   `CLASSES` map), so deleting on a guess is how the styles that audit exists
   to protect got deleted the first time.
7. **Bun has never been run,** despite ADR 0006. Same blocker as item 1.
