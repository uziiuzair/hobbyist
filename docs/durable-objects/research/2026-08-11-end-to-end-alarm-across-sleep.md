# An alarm set before sleep, fired after it

Status: NOTES. One real run on one machine, plus one defect it found in the
`worker` kind. The defect is fixed; the run is a single sample and is not a
benchmark.
Date:   2026-08-11

Everything in `packages/do` is tested against real SQLite files with no Docker,
no workerd and no clock. That is the right way to test a decision table and it
is not evidence the feature works. This is the run that closes the gap named in
`claude_docs/PROGRESS.md`: set an alarm, let the worker sleep, and see whether
it fires anyway.

It does.

## Method

A Worker with one Durable Object class, `Ticker`, which:

- on `GET /arm?in=<ms>`, calls `ctx.storage.setAlarm(Date.now() + ms)`
- in `alarm()`, inserts `Date.now()` into its own SQLite table
- on `GET /fired`, returns those rows and `ctx.storage.getAlarm()`

The timestamp is written from **inside** `alarm()`, which is what makes the
result unfakeable by the harness. A row whose `at` is later than the moment the
container was stopped can only exist if workerd ran that handler after the
sleep, and the container is never touched over HTTP between the stop and the
wake.

The harness drives the real `createWorkerResource`, `startWorker` and
`stopWorker` against a real Docker runtime, then starts the real
`startAlarmMirror` with the same enumerator the daemon passes it, and polls
**docker** for the container's state rather than the worker's HTTP port.

It does **not** run inside `hobby daemon`, because a daemon already held the
box-wide lock at `/tmp/hobby-daemon.lock` and it was the author's own. That
leaves exactly three lines untested by this run: the `startAlarmMirror` call in
`packages/cli/src/daemon/server.ts` and its drain in `performShutdown`.
Everything underneath them is exercised for real.

The store is a temporary one, which is precisely the hazard
`packages/cli/src/daemon/single-instance.ts` exists to prevent: two stores
allocate host ports blind to each other. It was safe here only because the
running daemon holds Postgres resources (15432 to 25432) and the worker range
is 35433 to 45432, checked before the run. That is a coincidence, not a method.
Anyone repeating this should stop the other daemon instead.

Five things this confirms that were previously only argued for:

1. **The deadline on disk is the deadline the worker set**, to 0ms. The
   nanosecond division in `alarms.ts` is exact against a live value, not just
   against a fixture.
2. **`actor_name` survives**, so the catalog can show `the-one` rather than 64
   hex characters, read out of a container that is not running.
3. **The directory really is `<resourceId>-<ClassName>`**, generated by
   `uniqueKeyFor` and parsed by `parseUniqueKey`, against a real Miniflare.
4. **workerd fires the alarm itself on startup.** The mirror only asked for a
   wake; nothing in `@hobby.sh/do` calls the handler.
5. **The row is deleted after firing**, so a fired alarm cannot wake the box
   forever.

## The guard, separately, against a live container

The run above only ever saw the guard answer `idle`, which proves nothing: a
guard that can only say yes is not a guard. A second run against a running
worker exercised the other half.

```
    no alarm             -> idle
    alarm 90s out        -> idle
    alarm 10s out        -> active
    same alarm, 1s grace -> idle
```

The last line is the one worth keeping. The same pending alarm flips the answer
when the window changes, which pins that the **window** is deciding rather than
the mere existence of an alarm. Without it, a guard that returned `active` for
any pending alarm at all would pass the first three lines and would pin awake,
forever, any worker with a recurring daily task.

## The number that is not a benchmark

**235ms late is one sample and is not the figure to quote.** The mirror polls,
so lateness is bounded by the tick interval and is otherwise arbitrary: an
alarm due just after a tick waits nearly a full interval. With
`ALARM_MIRROR_TICK_MS` at 10 seconds, worst case lateness is ~10 seconds plus
the worker's cold start (p95 321ms, `docs/compute/research/2026-08-10-http-cold-start-measurements.md`).
This run happened to land near the top of a tick.

Whether ~10 seconds of lateness is acceptable is not answered here. For a
cron-shaped workload it plainly is. For anything finer, the tick is the knob,
and shortening it costs one read-only SQLite query per sleeping namespace per
tick.

## The defect this found

**`bun build` could not resolve `cloudflare:workers`**, so no Durable Object
written the documented way could be deployed at all:

```
error: Could not resolve: "cloudflare:workers". Maybe you need to "bun install"?
    at /src/src/index.js:9:31
```

`import { DurableObject } from 'cloudflare:workers'` is how every current
Cloudflare example writes a Durable Object. The module is provided **by workerd
at runtime** and must be marked external rather than bundled. The fix is one
flag in `renderWorkerDockerfile`:

```
--external "cloudflare:*"
```

Worth dwelling on the failure mode, which is worse than the bug. It fails at
build time with a message telling the user to run `bun install`, so it reads
like the user got their imports wrong, when in fact the platform could not run
the syntax its own upstream documentation is written in. A user would plausibly
rewrite their Worker in the older `class X { constructor(state, env) }` style
and conclude Durable Objects here are an old dialect.

Pinned by a test in `packages/worker/test/worker.test.ts`, alongside the two
sibling findings from the compute session's own real runs (miniflare not
working under Bun, and workerd needing glibc). All three are the same shape:
invisible to every unit test, obvious on first contact with Docker.

## What this still does not tell us

- **Nothing about the daemon's own wiring.** Three lines in `server.ts` are
  untested by this run, for the lock reason above.
- **Nothing about more than one alarm, or more than one namespace.** One object,
  one class, one deadline.
- **Nothing about an alarm that fires while the box is off.** workerd reschedules
  on startup, so a deadline that passed during a daemon outage should fire on
  the next start, and that is untested.
- **Nothing about a five dollar VPS**, which is the machine this project is aimed
  at and where a 10 second tick plus a cold start is a larger fraction of the
  user's patience.
- **Nothing about the guard inside a real hibernation tick.** The guard was
  exercised directly, not by letting `startHibernator` reach it, so the
  `guardFor` dispatch is covered by unit tests only.
